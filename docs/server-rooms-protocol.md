# Server rooms: protocol and implementation spec (M1 + M2 server side)

Companion to `server-rooms-design.md` (approved, revision 3). This file is the contract between the room service
(`src/RoomServer`) and the client library (`src/OriCoop/Rooms`). The menus and save hooks come later and are not in
this spec. Never write a real server address in code, docs or tests: tests use localhost.

## Transport

- HTTP/1.1, `POST http://<server>:<port>/v1/<op>`, body = field list, response body = field list, always status 200 for
  application results (non-200 only for transport-level failures such as a wrong path).
- Default port 47021 (TCP). Server args: `--port N` (default 47021), `--data DIR` (default `./rooms-data`),
  `--prefix URL` (default `http://+:<port>/`; tests pass `http://127.0.0.1:<port>/`).
- Maximum request body 5 MiB. Save blobs at most `4*1024*1024 - 64` bytes (same as `SaveSync.MaximumSaveBytes`).

### Field list encoding (`RoomWire.Fields`)

An ordered list of (name, value) pairs. Each pair is `u8 nameLength`, `name` (ASCII), `u32 LE valueLength`, `value`
(raw bytes). Text values are UTF-8. Integers are decimal ASCII text. Booleans are `"1"`/`"0"`. Binary values (salt,
verifier, proof, nonce, save bytes) are raw bytes. Lists use indexed names: `save.0.id`, `save.0.name`, …, with
`save.count`. Unknown fields are ignored (forward compatibility).

`Fields` API (sketch): `Set(string name, string)`, `Set(string name, byte[])`, `Set(string name, long)`, `GetString`,
`GetBytes`, `GetLong(name, default)`, `Has`, `Encode() -> byte[]`, `static Decode(byte[]) -> Fields` (throws
`FormatException` on truncation).

### Every request

`proto` = `1`. `client` = free text (mod version), shown in server logs.

### Every response

`ok` = `1`, or `ok` = `0` with `error` = one of the codes below and `message` = short English text.

| error | meaning |
|---|---|
| `bad_request` | missing or invalid field |
| `old_client` | `proto` not supported |
| `no_room` | room id or code not found (also used for a cleared code) |
| `bad_password` | proof wrong |
| `locked` | too many wrong passwords or unknown join codes from this IP; `retry` = seconds |
| `bad_token` | token does not match this member (client then asks for the password and calls `rebind`) |
| `not_member` | steam id is neither P1 nor P2 |
| `already_member` | join by someone already in the room; response still carries `room` |
| `forbidden` | role may not do this (e.g. P2 kicking) |
| `busy` | the save is held by the other member (for `delete_save`, `revert`) |
| `not_host` | upload by someone who does not hold the lease |
| `version_conflict` | `base` ≠ current version; response carries `version` |
| `limit` | rooms per Steam id (50), saves per room (20) |
| `too_large` | save blob over the limit |
| `solo_off` | (not an error path normally; see `enter`) |

## Identity and passwords

- `steam` = SteamID64 as decimal text. `nick` = display name, ≤ 32 chars.
- Password key: `verifier = PBKDF2-HMAC-SHA1(UTF8(password), salt, 20000 iterations, 32 bytes)` (`Rfc2898DeriveBytes`).
  `salt` = 16 random bytes, generated by the client at create / set_password / copy / restore. The server stores salt
  + verifier only. Passwords are at least 4 characters (client-side check; server checks verifier length 32).
- Login proof: the client calls `challenge` to get `salt` and a one-time `nonce` (16 random bytes, valid 120 s, single
  use, server keeps at most 10000 outstanding), then sends `proof = HMACSHA256(key: verifier, data: nonce)`.
- Wrong proof: per client IP, 5 failures inside 15 minutes lock that IP out of password ops for 15 minutes (`locked`).
  Since the T-173 review a `join` or `challenge` by an unknown, closed or expired code counts as a failure in the same
  lockout (the code is an open room's only secret), and a locked IP is refused before the code is looked up, also for
  open rooms. A full open room's (right) code does not count.
  Success does not reset the counter early (keep it simple).
- Token: 32 random bytes as lowercase hex (64 chars), returned on create/join/rebind/copy/restore. The server stores
  `SHA256(token)` hex, up to 4 per member (oldest dropped), so one player can use several PCs. Authenticated ops send
  `room`, `steam`, `token`.
- Room id: `r` + 24 lowercase hex chars. Save id: `s` + 16 lowercase hex chars. Join code: 6 chars from
  `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (the alphabet the removed relay used), unique across live rooms, case-insensitive on input.
- Comparisons of proofs/token hashes use a constant-time compare.

## Seats (up to 4 members; supersedes every "P1/P2" below)

Planned for the four-player design (`four-player-design.md` section 6, not yet approved), so the data model holds up
to 4 members now, while the default behaves exactly like the approved 2-player design.

- Room has `seats` = capacity, 2–4, default 2 (`set_seats`, seat 1 only, cannot go below the current member count).
- Members list: up to 4 entries `{ seat (1–4), steam, nick, token hashes (≤4) }`. Seat 1 = creator ("P1"). A joiner
  takes the lowest free seat number. In fields: `m.count`, `m.N.seat`, `m.N.steam`, `m.N.nick`.
- `role` in replies is the seat number as text (`"1"`…`"4"`); the client maps 1 → P1, 2 → P2, etc.
- Join code exists while members < seats, is cleared when the room is full, and is regenerated (a new random code)
  whenever a member leaves or is kicked and the room was full; while the room is not full the existing
  code stays. A cleared code (room full or deleted) goes back to the pool and may later be given to another room, as
  after a restart (T-124). When no free code is found after a bounded number of tries, `create` and `copy` fail with
  `limit`; a room that reopens without a free code stays codeless until its next membership change.
- `kick` takes `seat`: seat 1 may kick any other seat; others get `forbidden`. `quit`: any seat except 1. When the last
  member quits (a `copy` placed in seat 2-4 can leave a room with one non-seat-1 member) the room is deleted (moved to
  trash), never stored without members (T-122).
- "Rooms per Steam id" counts rooms where the Steam id has any seat.
- Lease: one holder per save; every other member entering gets `mode=join` with the holder's `live` code. With
  `solo`=0, "nobody else present" means no other member has waited on this save in the last 15 s.
- Played seconds: `secs.seat.N` per seat plus `secs.both` for together play (upload `together`=1 when ≥2 players were
  in the session). Info shows `save.N.secs.seat.K` for each seat that has played.
- `copy`: the caller picks `seat` in the new room (default 1); the new room gets `seats` from the source room.
- `restore`: sends `m.count`/`m.N.*` and `seats` instead of p1/p2; caller must be one of the members; the code is
  empty only if members = seats.
- The client library exposes seats generically; the menus will only offer 2 seats until the four-player design is
  approved.

## Room and save state (server)

Room: `id`, `name` (≤ 32 chars), `code` (empty when P2 is set), `salt`, `verifier`, `p1`, `p1nick`, `p2`, `p2nick`,
`tokens.p1.*`, `tokens.p2.*`, `solo` (1 default), `created`, `played` (unix seconds UTC), `origin` (text, e.g.
`copy of r…/s… v41`, `restored`), and its saves.

Save: `id`, `name` (≤ 32 chars), `version` (starts at 1 when created with bytes, 0 if created empty for a new game),
`summary` (opaque client text ≤ 512 bytes), `by` (steam of last uploader), `at` (unix seconds of last upload),
`secs.p1`, `secs.p2`, `secs.both` (played seconds), `origin` (text), and a lease: `holder` (steam or empty), `live`
(live join code text ≤ 16, may be empty; since T-159 the host's C-server room code, before that a relay code), `beat` (unix seconds of the last enter/beat/live/upload by the holder),
and `waiting` (steam + time, used when solo is off).

Lease expiry: 90 s without a beat (server field `LeaseSeconds`, settable for tests). Clients beat every 30 s.

### enter (lease rules)

Let `me` = caller, `other` = the other member.

1. Lease held by `other` and live → `mode=join`, `live` = the holder's live code (C-server room code) (may be empty: the client polls `beat`
   until it is not).
2. Lease free, expired, or held by `me` → if `solo`=1, or the room has no `other`, or `other` waited on this save
   within the last 15 s → `me` becomes holder, `mode=host`. Otherwise (`solo`=0 and nobody waiting) → `me` is recorded
   as waiting, `mode=wait`; the client calls `beat` with `waiting=1` every 5 s and the answer changes once the other
   player enters (the second to arrive becomes host, the first then sees `join`).
3. Different saves of one room have independent leases.

### History and trash

- Per save keep the last 30 versions plus, for older ones, the newest version of each UTC day for 30 days; prune after
  each upload/revert.
- Trash: deleted rooms/saves move to `<data>/trash/<unix>-<id>`; entries older than 30 days are deleted at startup and
  once an hour.

### Storage layout and durability

```
<data>/rooms/<roomId>/room.dat              Fields-encoded room record (includes the save list metadata)
<data>/rooms/<roomId>/<saveId>/current.sav
<data>/rooms/<roomId>/<saveId>/v<version>.sav   history (current version is also present as v<N>.sav)
<data>/trash/...
```

Every write goes to `<file>.tmp` then replaces the target (`File.Replace` when the target exists, else `File.Move`). The
server loads all room records at startup (codes, counts) and keeps them in memory, so a restart keeps everything
(tests restart the server on the same data dir). Leases and nonces are memory-only (lost on restart, which is fine).

Startup skips a room record it cannot read (torn write, invalid members) with a `skip_room <dir> <error>` log line and
serves every other room; the files stay for a manual look (T-122).

### Concurrency, timeouts and limits (T-123, T-124)

Every request runs on its own worker; only the room logic (state and room files) runs under one lock, so a slow or
half-open connection never holds up other clients. Reading a request body or writing a reply may pause at most
`ReadTimeoutSeconds` (15) at a time and take at most `RequestTimeoutSeconds` (120, the client's transfer timeout) in
total; then the connection is dropped (result `timeout` in the log). At most `MaximumConcurrentRequests` (64) requests
run at once; more are dropped (`server_busy`). A body with more than `RoomWire.MaximumFields` (65,536) fields is
refused as `bad_request` while decoding (the largest real record has about 5,100); field lookup is O(1).

Logging: one console line per request: time, op, room id, result. Never log passwords, verifiers, proofs or tokens.

### RoomLocalStore

`new RoomLocalStore(string rootFolder)`; layout per design doc 2.3:

```
<root>/<roomId>/room.dat     Fields: server (as given by the caller; local only), id, name, role, steam, p1, p1nick, p2, p2nick, solo, saves list (id, name, version, summary)
<root>/<roomId>/token        token text
```

## T-173 room numbers

Each room has a display number `no` (decimal integer), starting at 1001 per server and increasing for new rooms
(including password rooms, copies and restores). `create`, `join` and `info` return it; `copy` and `restore` also return
it in their usual creation reply. The number is stored in `room.dat`. Startup resumes at `max(existing no) + 1`
(at least 1001); old records without `no` receive numbers in `created` order, with room id breaking ties, and are
persisted before requests are accepted. Numbers identify rooms for display, not authentication or joining; invite
codes remain the join mechanism. Deleted-room numbers are not separately reserved across restarts.

The local room backup stores `no` and `played` for the MyRooms list's display and newest-played-first ordering.
MyRooms uses the existing job queue, token store and RoomSession; successful password-free create/join opens info
and enters the first save; the picked co-op slot is linked to the new room (its `.oriroom` sidecar) so the room is
hosted from that slot. A create / join / enter reports success only once the room session hosts or joins, and an
error for anything before that (enter, download, slot); a cancelled one reports nothing. An existing member that
gets `already_member` from an older server reuses its locally stored token. 删除 decides delete (seat 1) or quit
from fresh info of that room, or its stored member list, and forgets the local record when the server answers
`no_room` / `bad_token` / `not_member`. The room list shows only rooms of the selected room service. A failed
`confirm` is remembered (file `confirm` in the room's local folder) and resent whenever fresh info of that room says it
is still pending (我的房间 menu refresh, room page refresh, and an info check every 30 seconds while the room session
runs in game) until info says the room is confirmed; info that says confirmed only clears the marker, so a reopened
code is never closed by a late retry. A room session error while a create / join / enter still waits for it to start
ends that session (no join or holder session after the error was shown). Creating from the title slot picker reads the co-op folder's selected save; an empty slot reports
`no_save` (localized `rooms.err.no_save`), since new-game rooms are not supported yet. Room-page info refreshes every
five seconds, and confirm/open_code update the displayed state on success. The original password helpers remain
available for old rooms.

## T-173 open rooms

This section supersedes the password and automatic join-code rules above **only for open rooms**. Existing password
rooms, including `copy` and `restore`, keep their existing behaviour.

- `create` may omit both `salt` and `verifier`. Such a room stores `open=1`, `pending=1` and immediately reserves a
  join code. Providing credentials still requires both valid fields and creates a password room (`open=0`,
  `pending=0`). A pending room's code has no expiry, including when it is full.
- `challenge` with an open room's active code returns `room`, `open=1`, with **no** `salt` or `nonce`.
- `join` with an open room's code sends only `code`, `steam`, `nick`; no nonce or proof is required. The code must
  still be open (pending, or `now < code_until`), and there must be a free seat. A closed/expired/unknown code or a
  full room returns `no_room` (unknown/closed/expired codes count toward the IP lockout, see above). An existing
  member using an active code gets a fresh token for its seat (open rooms have no `rebind`, so this is how a lost
  token is recovered; older tokens stay valid). Successful join returns the usual `room`, `token`, `role`.
- `create` takes an optional `seats` (2-4, otherwise `bad_request`); without it a room has 2 seats as before.
  我的房间 creates its open rooms with `seats`=4, like the C-server room they play in.

| op | request | rules | response |
|---|---|---|---|
| `confirm` | A (`room`, `steam`, `token`) | any member of an open room; sets `pending=0`, closes and releases the code; repeated calls succeed | — |
| `open_code` | A | any member of an open room with a free seat; otherwise `forbidden`; reuse an active code or reserve a new one (`limit` if none is available); set `code_until=now+300` | `code`, `expires` (Unix seconds UTC), `now` (server time, Unix seconds) |

`confirm` is sent when the creator presses start. The server allows any authenticated member to confirm. Calling it
again also closes any subsequently reopened code. Password rooms reject both new operations with `forbidden`.
`open_code` does not confirm a pending room: pending codes remain non-expiring until confirmation, regardless of
`code_until`.

`info` always includes `open` (1/0), `pending` (1/0), `code_expires` (Unix seconds UTC, 0 when no code or while
pending) and `now` (the server's current Unix time; clients count `code_expires` down from the server's clock
difference, never from their own clock). Every open-room member sees the active `code`; password-room codes remain
visible only to seat 1.
Filling a room, quitting, kicking or changing capacity does not change an open room's code lifecycle: membership
changes never reopen a closed code. A code remains reserved until confirmation, window expiry or room deletion.

The server exposes `CodeOpenSeconds` (default 300) and `PendingSeconds` (default 21600) for tests. Unconfirmed open
rooms whose age reaches `PendingSeconds` are moved to trash, releasing their code, just like `delete_room`.
Seat 1 may also delete a pending room normally. Code expiry and pending-room cleanup run lazily on room/code
lookup (including `challenge`, `join`, `info`) and in the existing hourly maintenance. Expired codes are cleared,
released and persisted. `open`, `pending`, `code_until` are stored in the Fields-encoded `room.dat`; startup keeps
pending code reservations, closes expired windows and trashes overdue pending rooms before accepting requests.
Old records without these fields are password rooms.

Client additions (all return `RoomReply`; `OpenCode` results are in `Fields[code]` / `Fields[expires]`):

The original `Create(..., password, ...)` also creates an open room when `password` is null. The existing four-argument
`Join` still uses password proof for password rooms, and skips proof when the challenge says `open=1`.
Three-argument `Join` challenges first and reports `bad_request` (password required) for a password room; callers can
use the existing password overload. `rebind` is password-only and returns `forbidden` for an open room; an open-room
member recovers a lost token by joining again with an open code (see above).

`RoomTest` adds real HTTP checks for pending creation, authenticated operations, password-free challenges/joins,
existing members, confirmation and code release, five-minute reopening/renewal, full-room refusal, membership
changes, lazy expiry, pending trash, restart reservations/windows, startup cleanup and hourly maintenance.
Existing password-room checks remain unchanged. The T-173 review changed one open-room check (an existing member joining with an open code now gets a fresh token instead of `already_member`) and added checks for the code lockout, create `seats`, the server clock (`now`) and the 我的房间 rules.
